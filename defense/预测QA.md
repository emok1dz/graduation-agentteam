## 一、技术选型

### Q1 为什么选择零第三方依赖？不用 Express、Vue 不是“重复造轮子”吗？

- 这是需求阶段确定的约束（C-01、C-02），目的有三：一是部署简单，不需要 `npm install`，一条 `npm start` 即可运行；二是没有供应链安全风险和版本漂移；三是作为毕业设计，路由、鉴权、原子写盘、判分等关键代码都是自己实现的，每一行都能讲清原理。
- 需要的能力其实很有限：路由只要“方法 + 路径参数 + 角色声明”，约 100 行即可；加密、文件、测试都由 Node 内置模块提供（`node:crypto`、`node:fs`、`node:test`）。
- 代价是开发量更大、生态便利性少，若做成生产系统，会考虑引入成熟框架。

### Q2 为什么用 JSON 文件而不用 MySQL？

- 课题规模（约 1000 用户、2000 题、5000 答卷，单场 ≤200 人）可全量放进内存，查询就是内存遍历，测试中普通查询平均 1.7~12.3ms，远低于 300ms 要求。
- 零依赖、单进程部署，数据文件可直接打开查看，便于演示和调试。
- 针对 JSON 的弱点做了处理：全局事务互斥锁防并发覆盖；写临时文件 → fsync → rename 原子替换防写坏；多次写合并为一次落盘。
- 留了迁移路径：仓储层统一接口，`design/database/ddl.sql` 已给出 MySQL 8 建表脚本，迁移只需新增一套 MySQL 仓储实现并改 `STORAGE` 配置，服务层、控制器、前端都不改。

### Q3 JSON 存储最大的问题是什么？什么时候必须换数据库？

- 每次写事务都要整文件序列化落盘，写延迟随数据量线性增长。测试中在 25000 条作答的规模下，200 并发保存 P95 约 1.24s，满足 100% 成功率要求，但数据再大就会变慢。
- 另外只能单进程，无法水平扩展。
- 当数据量明显超过需求规模、或需要多实例部署时，应迁移 MySQL 或改为增量持久化。

### Q4 为什么用服务端会话而不用 JWT？

- 需求要求退出、禁用、改密后令牌**立即失效**（NFR-05）。JWT 是无状态的，签发后在过期前无法吊销，除非再加黑名单，等于又回到服务端状态。
- 服务端会话表可直接删除记录实现即时吊销，且库内只存令牌的 SHA-256，数据泄露也拿不到可用令牌。

### Q5 前端为什么不用框架？26 个页面怎么组织？

- 约束 C-02 要求原生 JS、无构建。用 hash 路由 + ES Module 按需 `import()` 加载页面模块，每个页面统一导出 `render / unmount`，`unmount` 负责清理倒计时、自动保存等定时器。
- 统一封装了 DOM 构造函数 `h()`、表格、分页、弹窗、表单组件；62 个接口在 `api.js` 中按契约 operationId 同名封装。
- 好处是首屏只有 75.6KB、可交互 134ms（要求 ≤300KB、≤2s）。

## 二、并发与一致性

### Q6 学生重复点击交卷或网络重发，怎么保证只交一次？

- 前端：确认后按钮立即禁用。
- 后端是关键：交卷在事务互斥锁内检查答卷状态，只有“作答中”才能交卷；其余情况一律返回 409/40904 并带回原交卷结果，交卷时间不变，即幂等。
- 数据层面同一考试同一学生只有一条答卷（`exam_id + student_id` 唯一）。
- 测试 IT-ANS-07：同一答卷 10 个并发交卷请求，1 个 200、9 个 40904，库内仅 1 条答卷。

### Q7 多个学生同时保存答案，会不会互相覆盖？

- 所有写操作都包在 `repos.transaction()` 内，在全局互斥锁中串行执行“读-校验-写”，且每个学生只写自己的答卷；事务出错整体回滚。
- 性能测试中 200 名学生并发保存、200 名并发交卷，成功率 100%，逐份核对 200 份答卷的作答内容与手算得分全部一致。

### Q8 全局锁串行执行不会成为性能瓶颈吗？

- Node 是单线程事件循环，事务内主要是内存操作，很快；瓶颈在落盘。我们做了写合并：同一时间窗内的多个事务合并为一次落盘。测试中 50 个并发事务的实际写盘次数小于 50。
- 在需求规模（单场 ≤200 人）下满足要求；规模更大时迁移到 MySQL，用行级锁 `SELECT … FOR UPDATE` 替代全局锁。

### Q9 写文件时服务器突然断电，数据会损坏吗？

- 不会产生“半截文件”：先写 `db.json.tmp`，`fsync` 后再 `rename` 原子替换，任意时刻磁盘上的 `db.json` 要么是旧版本要么是新版本。
- 测试 UT-STORE-05：30 次写入 200KB+ 文档期间并发循环读取，每次 `JSON.parse` 都成功；若文件确实损坏，系统拒绝启动且不改动原文件，防止误覆盖。

### Q10 学生不点交卷、直接关浏览器，或者考试时间到了怎么办？

- 前端倒计时归零自动交卷（`auto: true`）。
- 后端兜底：调度器每 30 秒扫描，超过“截止时刻 + 10 秒宽限”仍在作答中的答卷以已保存答案强制交卷（`forced`）并自动判分；考试结束后为没有答卷的学生生成缺考记录（`absent`）。另外在进入作答、监控、批改、统计等接口前也会对相关考试先扫描一次，不完全依赖定时器。

### Q11 学生能否通过修改电脑时间或请求参数延长考试？

- 不能。开始、截止、交卷时刻全部取服务端时间，请求体里的时间字段一律忽略；前端倒计时只是用服务器时间偏移校正后的显示。
- 测试中伪造 `submitted_at` 被忽略；超过截止 +10s 后保存返回 40906，新答案不被接受。

## 三、安全

### Q12 密码是怎么存储的？

- 使用 Node 内置的 scrypt 慢哈希（N=16384, r=8, p=1，输出 64 字节），每个用户 16 字节随机盐，比对用 `timingSafeEqual` 常量时间比较。
- 测试检查 `db.json`：5 个已知明文密码均未出现，每个用户只有 `password_hash` 和 `password_salt`，盐两两不同；同一密码两次哈希结果不同；单次哈希 ≥10ms。

### Q13 如何防止暴力破解？

- 同一账号连续 5 次密码错误锁定 10 分钟（42900），锁定期间正确密码也拒绝。
- 账号不存在时也执行一次 scrypt，响应时间一致，防止通过时间差枚举账号；提示统一为“账号或密码错误”。

### Q14 令牌如何生成和保护？被盗了怎么办？

- `randomBytes(32)` 生成 64 位十六进制令牌，只通过 `Authorization` 请求头传输，不放 URL；数据库只存 SHA-256。
- 空闲 2 小时过期，活跃时滑动续期；退出、禁用、重置密码删除全部会话，改密删除其他会话，旧令牌立即 401。
- 生产部署应放在 HTTPS 反向代理之后，防止传输中被窃取。

### Q15 怎么防止越权？比如学生调用教师接口、老师改别人的题？

- 两级校验：第一级路由表声明角色（RBAC），角色不符返回 40300；第二级服务层做资源归属校验，例如题目的 `teacher_id` 必须是当前教师、答卷的 `student_id` 必须是当前学生，否则 40301。前端隐藏按钮只是体验，不作为安全手段。
- 测试 IT-RBAC：学生调用 15 个教师/管理员接口均 403；teacher2 读/改/删 teacher1 的题、卷、考试、监控、批改、统计均 403。

### Q16 如何防 XSS？

- 前端所有用户内容只通过 `textContent` / `h()` 渲染，代码中没有 `innerHTML`、`eval`、`document.write`。
- 服务端返回严格 CSP：`default-src 'self'`，禁止内联脚本与样式，即使有漏网也无法执行。
- E2E 测试中题干写入 `<script>` 和 `<img onerror>`，在题库、预览、作答、成绩页面都原样显示为文本，脚本从未执行，无 CSP 违规。

### Q17 什么是 CSV 注入？你们怎么处理？

- 导出的 CSV 用 Excel 打开时，以 `=`、`+`、`-`、`@` 开头的单元格会被当作公式执行，可能被利用构造恶意链接。
- 测试工程师用姓名 `=1+2` 发现导出时原样写出，记为低严重度缺陷（需要管理员录入恶意姓名且教师允许公式执行才能触发）。修复方法是在 CSV 转义函数中对危险前缀的单元格前加单引号，已修复并回归通过。

### Q18 考试期间学生能不能从接口里拿到答案？

- 不能。学生作答接口使用独立的白名单视图，只返回题号、题型、题干、选项、分值、空数等 7 个字段；成绩发布前分数为 null；教师可设置不允许回顾时不返回题目。
- 测试中抓取学生端相关接口响应，搜索 answer、analysis、参考答案等关键词均为空。

## 四、防作弊

### Q19 系统有哪些防作弊措施？

- 时间防篡改：一切时间以服务端为准，超时后答案不被接受。
- 答案保密：作答期间接口不含任何答案和解析；成绩发布前看不到分数。
- 一人一卷一次：每名学生每场只能作答一次，交卷幂等。
- 随机组卷：可按规则从题库随机抽题；考试可开启选项乱序（以答卷 ID 为种子，每人顺序不同但判分不受影响）。
- 权限隔离：学生只能看到本班考试和本人答卷。

### Q20 为什么没有做切屏检测、人脸识别？

- 需求阶段明确列为不纳入范围：视频监考、人脸识别属于硬件/生物识别手段，超出本科毕设规模；而切屏检测在浏览器中很容易被绕过，只能起提示作用。
- 作为后续改进方向：可加入切屏/失焦次数记录并在监控页展示，由教师判断。

## 五、自动判分

### Q21 多选题少选了能得部分分吗？为什么这样设计？

- 不能。本系统多选题规则是与标准答案**完全一致**才得满分，少选、多选、错选均 0 分。这是需求假设 A-05 明确规定的，和多数标准化考试的做法一致，规则简单、无歧义。
- 实现上先把作答排序，再与标准答案比较；单元测试 UT-SCORE-03/04 覆盖了完全一致、少选、多选、错选、空数组、非数组等情况。
- 若需要部分得分（如“少选得一半”），只需修改 domain 层的纯函数 `scoring.mjs` 并增加配置项，影响范围很小。

### Q22 填空题怎么判？分值除不尽怎么办？

- 逐空比对：去掉首尾空格、忽略英文大小写，每个空可以配置多个可接受答案（如“后进先出”和“LIFO”）。
- 分值按空拆分，保留 1 位小数，最后一空补差，保证合计恒等于总分，例如 10 分 3 空拆为 3.3、3.3、3.4。

### Q23 简答题怎么评分？

- 交卷时简答题得分为空，答卷进入“待批改”状态；教师可按学生或按题目批改，给分并写评语。
- 全部批改完成且考试结束后才能发布成绩；发布后还可撤回。

## 六、性能与扩展

### Q24 系统性能怎么样？测试是怎么做的？

- 构造 1000 用户、2000 题、102 场考试、5000 答卷、25000 条作答的规模数据，各接口串行调用 100 次统计耗时。
- 普通查询平均 1.7~12.3ms（要求 ≤300ms），统计接口 2.3~3.5ms（要求 ≤1s）。
- 200 并发保存与交卷成功率 100%，P95 分别为 1240.1ms、1358.4ms；100 并发登录 P95 1223.3ms，主要耗在 scrypt 慢哈希，这是安全性的预期代价。

### Q25 如果要支持上万人同时考试，怎么扩展？

- 存储迁移 MySQL（DDL 已有），事务映射为数据库事务 + 行级锁；会话放到 Redis，使服务无状态，多实例 + 负载均衡水平扩展。
- 静态资源走 CDN；判分和统计可异步化；自动保存可做客户端批量合并。
- 因为分层清晰、仓储接口统一，这些改动主要集中在仓储层和部署层。

## 七、测试

### Q26 你们的测试覆盖率是多少？怎么保证测试数据可信？

- 后端 134 条单元/集成/非功能用例，加 8 条 E2E，共 142 条，失败 0；源码覆盖率行 96.70%、分支 87.70%、函数 95.02%（排除测试文件本身统计）。
- 全部使用 Node 内置 `node:test`；每个测试文件独立进程、独立临时数据目录、随机端口，互不干扰。
- 统计类用例在注释中写出手算过程逐项比对，例如平均分 (21+9+15.5+0)/4 = 11.375 → 11.38。

### Q27 和时间有关的功能（开考、截止、锁定）怎么测？

- 后端所有业务时间都从可注入的时钟模块获取，测试中用假时钟 `setNow / advance` 精确推进，比如验证截止后 +10000ms 仍可交卷、+10001ms 就过期。不用真的等待，测试稳定可复现。

### Q28 测试中发现了哪些问题？

- 发现 2 个低严重度缺陷：一是缺考学生在考试结束后进入考试，提示的是“已交卷”而不是“不在考试时间内”；二是 CSV 导出没有防公式注入。两者都不影响数据和判分，已修复并回归通过。
- 处理流程：测试先按期望行为写用例并标记为已知缺陷，退回开发修复，修复后用例转为通过，形成闭环。

## 八、AI 智能体团队协作

### Q29 AI 智能体团队在项目中起了什么作用？你自己做了什么？

- 采用“智能体团队”分工：组长、需求分析师、系统架构师、前端、后端、测试、论文、答辩助手 8 个角色，每个角色只负责自己的目录，按“需求 → 设计 → 开发 → 测试 → 论文/答辩”分阶段推进，每阶段由组长验收。
- 角色之间通过**契约文件**衔接：需求规格 → OpenAPI 契约（62 个接口）→ 代码 → 测试报告，避免各说各话。测试发现缺陷后退回开发修复，再回归。
- 人工把关【实际情况】：本人负责确定题目方向和技术约束、审阅各阶段产出并做验收决策、亲自运行启动与测试命令核对报告数字、通读并理解核心代码（路由、鉴权、事务与原子写、判分、统计），能够独立讲解与修改。

### Q30 用 AI 生成的代码，怎么保证质量和你真的掌握？

- 质量靠流程而不是靠信任：需求逐条编号并有追踪矩阵；接口以契约为唯一依据；142 条自动化测试、96.70% 行覆盖率；性能、安全都有可复现的测试；测试数字全部来自真实运行输出。
- 掌握程度：选型刻意零依赖，关键机制都在项目源码中、没有黑盒框架，可以现场打开代码讲解任一模块，例如交卷幂等的事务实现、scrypt 密码校验、多选判分函数。

## 九、不足与改进

### Q31 项目还有哪些不足？

- 存储：JSON 整文件落盘，写延迟随数据量增长，不能多实例部署。
- 兼容性：测试只在 Node 22 + Chromium 下进行，Node 18/20、Firefox、Edge 未实测；前端本地草稿恢复未做专项自动化测试。
- 功能：没有切屏检测等防作弊手段；不支持题目图片、公式、编程题；不支持补考/重考。
- 部署：未在 HTTPS 反向代理环境中实际验证。

### Q32 如果继续做，下一步做什么？

- 第一优先：实现 MySQL 仓储并做迁移脚本，解决写放大和扩展性问题。
- 第二：补齐多浏览器与 Node 18/20 兼容性测试、前端草稿恢复测试。
- 第三：功能扩展——题目富文本/图片、编程题在线判题、切屏记录、补考、消息通知。
